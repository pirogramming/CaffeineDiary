2. accounts 앱 - 인증 API

전부 @api_view 함수형 뷰 (accounts/views.py). 세션 인증(SessionAuthentication) 기반.

MethodURL권한Request Body성공 응답실패 응답
POST /auth/signup/ AllowAny {"username": str, "password": str} 201
{"user_id": int, "username": str, "has_profile": false, "next": "/signup/profile"}		 - (입력 검증 TODO 미구현: username 중복, 빈값 등 아직 안 막힘)
POST /auth/login/ AllowAny {"username": str, "password": str} 200
{"user_id": int, "username": str, "has_profile": bool, "next": "/" or "/signup/profile"}		 400 {"code": "INVALID_INPUT", "message": "..."} (필드 누락)
401 {"code": "INVALID_CREDENTIALS", "message": "..."} (인증 실패)
POST /auth/logout/ IsAuthenticated - 200
{"success": true, "night_session_active": true, "next": "/login"}		 401 {"code": "NOT_AUTHENTICATED", "message": "로그인 상태가 아닙니다."} (미로그인)
GET /auth/session/ AllowAny (+ CSRF 쿠키 발급) - 200
미인증: {"is_authenticated": false, "user_id": null, "has_profile": false, "next": "/login"}
인증됨: {"is_authenticated": true, "user_id": int, "has_profile": bool, "next": "/" or "/signup/profile"}		 -

has_profile은 accounts/views.py의 _has_profile()이 계산하는데, 지금은 TODO 상태로 항상 False를 반환합니다. UserProfile 모델(body_weight_kg, target_sleeptime, profile_image)은 만들어져 있지만 실제 존재 여부를 확인하는 로직은 아직 없습니다.

logout의 night_session_active도 로직 없이 항상 true로 고정된 값입니다. (allnight 기능 연동 전 임시값으로 보임)

3. diary 앱 - 음료(Drink) API

DRF 제네릭 클래스 뷰 (diary/views.py). 전부 IsAuthenticated 필요, 응답은 요청 유저 소유 데이터로 자동 필터링됩니다.

MethodURLViewRequest Body성공 응답비고
GET /users/me/drinks/ DrinkListCreateView - 200
[DrinkSerializer, ...] (즐겨찾기 우선 → 최신순)		 본인의 is_active=True 음료만
POST /users/me/drinks/ DrinkListCreateView {"type": str, "brand": str, "name": str, "size": str, "caffeine_mg": int, "is_favorite"?: bool} 201 DrinkSerializer 이름/사이즈/카페인량 전부 직접 입력. 프리셋 브랜드를 골랐다면 size는 해당 브랜드 라벨과 일치해야 함(그 외 검증은 없음)
GET /users/me/drinks/<id>/ DrinkDetailView - 200 DrinkSerializer 남의 음료거나 삭제된 음료면 404
PATCH /users/me/drinks/<id>/ DrinkDetailView 수정할 필드만 (예: {"is_favorite": true}) 200 DrinkSerializer -
DELETE /users/me/drinks/<id>/ DrinkDetailView - 204 No Content 실제 삭제 아님. is_active=False로 소프트 삭제 (CaffeineLog의 drink_id 참조 유지 목적)
GET /users/me/drinks/presets/ PresetDrinkListView 쿼리파라미터 ?brand=starbucks (생략 시 전체) 200
[{"brand","brand_name","type","name","size","caffeine_mg"}, ...]		 DB 아님. presets 패키지의 상수 카탈로그. 카페인량 미입력 사이즈는 자동 제외
POST /users/me/drinks/from-preset/ DrinkFromPresetView {"brand": str, "name": str, "size"?: str, "is_favorite"?: bool} 201 DrinkSerializer (id, caffeine_mg 자동 포함) caffeine_mg는 절대 클라이언트가 안 보냄. 서버가 카탈로그(find_preset)에서 채움. 이미 같은 음료를 삭제했었다면 새로 만들지 않고 되살림

DrinkSerializer 응답 필드: id, type, type_display, brand, brand_display, name, size, caffeine_mg, is_favorite, is_recent, created_at

지원 브랜드 (프리셋 있음): starbucks, compose, baik, mammoth, ediya, mega, gongcha, pepsi, cocacola / custom은 프리셋 없이 자유 입력용

4. 사용자 흐름

가입 ~ 로그인

POST /auth/signup/  또는  POST /auth/login/
   -> 세션 쿠키 생성, has_profile로 다음 화면 안내(next)

새로고침 / 앱 재진입 시
GET /auth/session/  -> 로그인 유지 여부 확인

음료 등록 (두 갈래 중 선택)

[A] 카탈로그에서 선택
  GET  /users/me/drinks/presets/?brand=starbucks   -> 목록에서 이름/사이즈 고르기
  POST /users/me/drinks/from-preset/ {brand,name,size}
       -> caffeine_mg는 서버가 자동으로 채워서 응답

[B] 프리셋에 없는 음료를 직접 입력
  POST /users/me/drinks/ {type,brand,name,size,caffeine_mg}
       -> 전부 수동 입력

등록 이후 공통

GET    /users/me/drinks/          -> 내 음료 목록 (즐겨찾기 우선)
PATCH  /users/me/drinks/<id>/    -> 즐겨찾기 토글 등 수정
DELETE /users/me/drinks/<id>/    -> 소프트 삭제

6. 확인이 필요한 부분

  • /auth/social/ (django-allauth): config/urls.py에 include('allauth.urls')가 있지만, allauth 계열 앱이 INSTALLED_APPS에 없고 requirements.txt에도 없습니다(venv에는 설치되어 있음). SITE_ID, AUTHENTICATION_BACKENDS, allauth 미들웨어도 settings.py에 없어서 이 경로는 현재 서버 구동/요청 시 에러가 날 가능성이 있습니다. 실제로 열어보기 전엔 "구현됨"으로 보지 않는 게 안전합니다.
  • accounts/serializers.py 파일은 존재하지만 내용이 비어 있습니다. 지금 accounts 뷰들은 serializer 없이 request.data를 직접 다룹니다.
